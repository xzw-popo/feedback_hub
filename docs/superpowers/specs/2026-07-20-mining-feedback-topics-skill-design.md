# 通用反馈专题挖掘 Skill 设计

日期：2026-07-20

## 1. 目标

建设一个面向公司内部、可安装和分发的 Codex Skill。使用者只需用自然语言描述要查找的反馈专题，调用 Skill 的 AI 即可把需求整理成结构化专题定义，交给统一后台完成数据筛选、关键词与向量混合召回、批量语义判定、质量审计和结果导出。

首版 Skill 名称为 `mining-feedback-topics`。它不绑定 Win 工具栏、固定产品功能或固定标签体系。已完成的 Win 工具栏专题只作为回归验证样例。

## 2. 首版边界

首版面向能访问公司内部反馈后台的使用者，不要求脱离后台在任意 SQLite、CSV 或外部环境中独立运行。

首版交付的是可安装 Skill 包，不是新的专题反馈清单。为了让 Skill 能实际运行，本轮同时在现有 `feedback_hub` 中提供最小的专题挖掘后台入口，并复用已有反馈数据、搜索链路和向量召回工具；后台入口是 Skill 的运行依赖，不放入分发包，也不另建一套向量基础设施。Skill 被实际调用时，才根据用户请求生成相应专题结果。

首版不做：

- 固定专题看板或持续监控；
- 写回正式 L1/L2、严重度或专题标签；
- 修改远端生产反馈原文；
- 让调用 AI 直接操作数据库、向量集合、相似度阈值或 Excel 库；
- 建设新的向量模型、向量数据库或通用数据仓库；
- 面向公司外部环境的离线适配。

## 3. 方案比较

### 方案 A：纯说明型 Skill

只在 `SKILL.md` 中描述筛选方法，由每个调用 AI 自行写 SQL、调用向量工具、执行分类和导出。建设最快，但结果受模型能力和现场环境影响大，断点续跑、审计、安全和质量校验容易漂移。

### 方案 B：自包含重型 Skill

把数据库适配、向量检索、模型批处理和导出脚本全部放进 Skill。脱离后台也能运行，但会复制内部基础设施，携带较多依赖和配置，升级成本高，凭据与生产数据边界也更难控制。

### 方案 C：薄 Skill + 统一后台

Skill 负责专题定义、调用编排、边界复核和结果解释；后台负责所有确定性执行和批处理。Skill 只暴露稳定的高层命令，不暴露 SQL、向量参数和文件格式实现。

采用方案 C。它最符合内部首版的分发范围，也能把调用 AI 的要求从“懂数据库和检索工程”降到“能准确理解专题边界并输出结构化参数”。

## 4. 总体架构

系统分成三个边界清晰的单元：

1. **调用 AI 与 Skill**：理解用户需求，生成 `topic_spec`，调用后台，复核有限的边界样本，解释结果。
2. **专题挖掘后台**：作为 `feedback_hub` 的一个独立模块和稳定入口，读取数据、执行硬筛选和混合召回、拼接上下文、编排分类模型、生成复核队列、验证并导出结果。
3. **数据与检索基础设施**：正式反馈库、只读快照、BM25/关键词索引、向量数据库和内部模型服务。

向量相似度只负责找出可能相关的候选，不直接决定专题归属。最终准入必须经过结构化语义判定；确定性规则可以拒绝结构不合法的数据，也可以把可疑项送入复核队列，但不能仅凭相似度自动判定为命中。

## 5. Skill 包结构

分发源建议纳入当前仓库的 `codex-skills/mining-feedback-topics/`，用户安装时复制或通过内部仓库安装到个人 Codex skills 目录。新增这一正式目录时同步更新 `WORKSPACE_GUIDE.md`。

```text
mining-feedback-topics/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── scripts/
│   ├── validate_topic_spec.py
│   └── topic_backend_client.py
└── references/
    ├── topic-spec.md
    ├── topic-spec.schema.json
    ├── backend-contract.md
    └── review-policy.md
```

各文件职责：

- `SKILL.md`：保持精简，只规定调用顺序、停止条件、质量门和需要按需读取的参考文件。
- `agents/openai.yaml`：提供可发现的名称、简述和默认调用提示。
- `validate_topic_spec.py`：在请求后台之前，对专题定义做确定性结构和字段校验。
- `topic_backend_client.py`：封装鉴权、请求、状态轮询、产物下载和稳定错误码；不包含专题判断逻辑。
- `topic-spec.md`：解释字段语义和如何从用户需求构造正反边界。
- `topic-spec.schema.json`：供脚本和后台共同验证的机器可读契约。
- `backend-contract.md`：记录内部后台需要提供的能力和响应结构。
- `review-policy.md`：定义哪些样本必须进入 AI 边界复核，以及覆盖要求。

Skill 包不包含 README、安装指南、历史过程记录、真实反馈数据、密钥或向量模型。

## 6. 专题定义契约

`topic_spec` 只包含专题语义和业务范围，不包含 SQL、向量集合、相似度阈值、Top-K、批大小或模型名。核心结构为：

```yaml
schema_version: 1
topic_name: 全屏时工具栏不隐藏
objective: 找出视频或游戏全屏期间输入法工具栏仍显示或遮挡内容的反馈
scope:
  start_time: 2026-01-16T00:00:00+08:00
  end_time: 2026-07-16T14:00:00+08:00
  platforms: [Win]
  products: [微信输入法]
unit: feedback
inclusion_criteria:
  - 视频或游戏处于全屏、无边框全屏或独占全屏
  - 输入法工具栏仍然显示、置顶或遮挡内容
exclusion_criteria:
  - 仅描述游戏黑屏、切换桌面或输入失效
  - 仅描述 Windows 系统任务栏
positive_examples:
  - 玩游戏全屏后输入法工具条一直挡着
negative_examples:
  - 进入游戏以后黑屏
lexical_hints:
  objects: [工具栏, 悬浮栏, 状态栏]
  contexts: [全屏, 无边框, 独占, 游戏, 视频]
classification_labels:
  - id: matched
    meaning: 明确符合专题定义
  - id: not_matched
    meaning: 不符合或证据不足
output:
  preferred_format: xlsx
  required_fields: [feedback_text, feedback_time, source_url]
```

第一版只承诺 `feedback_text`、`feedback_time` 和 `source_url` 三个稳定输出字段；`required_fields` 必须是它们的非空子集。后台在接收规格时拒绝其他字段，并在 JSONL 中使用这些同名顶层键，Excel 中映射为“反馈原文”“反馈时间”和“对应链接”。

必填项是专题名称、目标、时间范围、至少一条纳入条件和至少一条排除条件。平台、产品、正反例和词语提示可以来自用户原始需求，也可以由调用 AI 补全。AI 不得伪造用户没有表达的产品范围；范围缺失且会显著改变结果时才向用户提问。

`lexical_hints` 是宽召回提示，不是命中规则。正反例用于构建向量查询和分类边界，不作为训练数据写回长期标签体系。

## 7. 后台能力契约

后台通过内部 API 或等价 CLI 暴露以下高层能力：

```text
capabilities
create-run <topic_spec>
get-run <run_id>
get-review-queue <run_id>
apply-overrides <run_id> <overrides>
export-run <run_id> <format>
verify-run <run_id>
```

### 7.1 数据和硬筛选

后台负责：

- 从受控数据源读取一致快照；
- 将来源字段映射到统一反馈结构；
- 执行时间、平台、产品、渠道、版本和非空文本过滤；
- 按反馈或会话粒度去重；
- 报告数据覆盖范围和缺口；
- 保持默认只读，不触发通用打标，也不写回正式标签。

### 7.2 混合召回

硬筛选后，后台执行关键词/BM25 与向量召回的并集，通过稳定融合策略排序和去重。首版沿用现有经验：

- 元数据条件先于语义检索执行；
- 关键词通道保证显式术语和精确表达；
- 向量通道补充口语、错别字、隐含场景和改写；
- 正例、专题定义和词语提示可以形成多个查询表示；
- 反例用于标记高风险近邻，不直接从候选中静默删除；
- 融合算法、阈值和候选上限由后台配置和版本化，调用 AI 不传这些参数；
- 每个候选记录命中通道、查询来源、原始排名和融合排名，便于审计。

### 7.3 上下文和语义判定

后台按会话或同一用户时间窗口拼接有限上下文，执行批量、结构化的语义分类。后台负责批大小、并发、重试、checkpoint、幂等、锁、JSON Schema 校验、成本统计和模型路由。

每个候选必须产生且只产生一条判定，至少包含：

```json
{
  "item_id": "feedback-id",
  "label": "matched",
  "confidence": 0.93,
  "evidence": ["全屏后工具栏一直显示"],
  "reason": "游戏全屏期间工具栏未隐藏",
  "needs_review": false
}
```

证据必须来自原始反馈或受控上下文。无充分证据时输出 `not_matched` 或 `needs_review=true`，不得根据产品常识补写事实。

### 7.4 复核和导出

后台生成有界复核队列，至少覆盖：

- 低置信度命中；
- 高置信度拒绝的随机样本；
- 只被向量通道召回的命中；
- 与反例高度相似的候选；
- 召回通道或证据规则相互冲突的候选；
- 每个最终分类的随机质量样本。

调用 AI 只审阅该队列并提交独立 override，不修改原始分类文件。后台合并 override 后重新验证并生成用户要求的结果文件和机器可读审计产物。

## 8. Skill 调用流程

Skill 被触发后按以下顺序执行：

1. 读取用户专题需求，识别目标问题、范围、时间、平台、纳入和排除边界。
2. 调用 `capabilities`，确认后台可用、数据覆盖满足目标、支持所需输出格式。
3. 构造 `topic_spec`；只有缺失信息会显著改变结果时才向用户提一个澄清问题。
4. 运行本地校验器。校验失败时修正专题定义，不提交半合法请求。
5. 创建专题运行并保存 `run_id`，轮询状态而不是重复创建运行。
6. 检查召回漏斗、失败项、覆盖范围和模型解析错误。后台存在未解决失败或数据缺口时停止交付。
7. 获取有界复核队列，依据原文和上下文提交结构化 override。
8. 要求后台合并复核、执行最终验证并按用户请求导出。
9. 向用户交付产物、统计口径、数据截止时间和已知限制。

调用 AI 不自行扫描全库、不自行实现向量检索、不在对话中批量粘贴候选、不绕过后台质量门，也不把一次性专题规则写入正式标签体系。

## 9. 调用 AI 的能力要求

普通专题调用者可使用中等能力、支持工具调用和结构化输出的模型。它必须能够：

- 从自然语言中区分现象、对象、触发场景和相邻但无关的问题；
- 写出有效 YAML/JSON；
- 根据校验错误修正字段；
- 阅读有限的原文与上下文并进行边界复核；
- 遵守运行状态、审计和停止条件。

数据库、SQL、embedding、向量距离、索引、并发、Excel 和断点续跑知识不属于调用 AI 的要求。复杂专题可以用更强模型负责专题定义和疑难复核；批量分类模型由后台单独选择。

## 10. 错误处理和安全

- 后台不可达、鉴权失败或能力版本不兼容：停止运行并报告明确错误，不退化为现场脚本扫描生产库。
- 数据覆盖不足：默认停止完整交付；只有用户明确接受部分范围时，才创建带缺口声明的运行。
- 向量索引落后于数据快照：后台必须报告索引水位；超出允许差值时停止混合召回。
- 分类调用失败或解析不完整：利用 checkpoint 重试；仍有 unresolved item 时不得导出“完整结果”。
- 重复提交：使用 `topic_spec` 哈希和幂等键复用现有运行，避免重复模型成本。
- 凭据：只从运行环境或内部连接器读取，不写入 Skill、日志、topic spec 或导出文件。
- 数据：原始反馈和个人标识仅按内部权限返回；Skill 不扩大用户已有的数据访问范围。
- 写操作：首版仅允许创建独立运行、审计和导出产物，不修改正式反馈及标签表。

## 11. 测试策略

Skill 按 process-documentation TDD 验证。

### 11.1 无 Skill 基线

用至少三个新上下文场景观察普通调用 AI 在没有 Skill 时的行为，保留原始输出：

1. 明确专题：Win 工具栏位置错乱与全屏不隐藏；
2. 相邻概念密集专题：区分输入法候选框、Windows 系统任务栏和输入法工具栏；
3. 范围信息不完整专题：缺少时间范围或平台，检验是否识别真正阻塞项。

记录它是否遗漏排除条件、直接把向量相似度当作命中、暴露底层检索参数、绕过质量门或产生不可审计结果。

### 11.2 Skill 验证

在新上下文中用相同场景加载 Skill，验证 AI 能否稳定：

- 生成符合 Schema 的 `topic_spec`；
- 正确使用后台高层能力；
- 不自行操作生产库和向量参数；
- 发现数据覆盖及索引水位问题；
- 完成有界复核并交付可追溯产物。

### 11.3 确定性测试

- 校验器测试必填字段、枚举、时区、空条件、重复 label 和非法输出字段；
- 后台 client 使用伪服务测试鉴权错误、版本不兼容、轮询、幂等和失败响应；
- Skill 目录通过官方 `quick_validate.py`；
- `agents/openai.yaml` 与 SKILL.md 的名称、描述和默认提示一致；
- Skill 包不包含密钥、真实反馈数据、模型文件或临时运行产物。

### 11.4 只读真实烟测

在不写正式库的前提下，用工具栏专题作为首个真实回归样例。验收重点是专题边界、运行审计和链接可追溯，而不是把历史结果数量硬编码为永久正确答案。

## 12. 验收标准

- Skill 能从内部仓库安装并被 Codex 正确发现和触发；
- 调用者只提供自然语言专题需求，不需要 SQL、向量和文件处理知识；
- 生成的 `topic_spec` 通过本地和后台同一 Schema 校验；
- 后台使用硬筛选、关键词/BM25 与向量混合召回，向量不直接决定最终命中；
- 每个最终结果可追溯到原始反馈、判定证据、运行版本和数据截止时间；
- 失败重试不会产生重复分类或重复模型调用；
- 未解决的数据缺口、索引滞后或分类失败会阻止完整交付；
- 首版不会触发通用打标，也不会写回正式标签或反馈表；
- 工具栏回归样例能复现已确认的纳入和排除边界，且 Skill 内不存在工具栏专用规则。

## 13. 后续扩展

首版稳定后，可以独立扩展：

- 本地 SQLite/CSV 数据适配器；
- 持续专题监控和定时增量运行；
- 主题结果写入看板前的审批流程；
- 历史正反样本记忆与专题模板库；
- 更多导出格式和专题分析报告。

这些扩展不进入首版实现计划。
