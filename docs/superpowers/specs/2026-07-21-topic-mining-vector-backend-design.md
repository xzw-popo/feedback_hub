# 通用反馈专题挖掘向量后台设计

日期：2026-07-21

## 1. 文档状态与关系

本文档补充并修订《通用反馈专题挖掘 Skill 设计》中尚未落地的数据同步、向量索引和检索服务能力。此前已经实现的专题编排后台与 Skill 契约继续保留；本设计负责把本地 Qwen3-Embedding-0.6B 实验生产化，并接入远端正式反馈库。

若两份设计存在冲突，以本文档中的下列决定为准：

- 建设远端向量基础能力，而不是继续把它视为既有依赖；
- 数据每 20 分钟拉取一次，每次拉取最近 30 分钟；
- 入库阶段仅按 `feedback_id` 精确幂等去重，不做语义删重；
- 第一版只建立单条反馈级索引，保留 `conversation_id` 供结果聚合；
- 用户未指定查询时间时默认最近两周；
- 标准模式最多由后台语义分类 500 条去重候选，最多返回 100 条代表性反馈；
- 内部接口仅在公司内网或 VPN 可访问，第一版不增加访问令牌认证。

## 2. 目标与非目标

### 2.1 目标

- 在现有 DevCloud 节点部署 Qwen3-Embedding-0.6B CPU 推理能力；
- 对正式反馈库做可恢复的全量回填和持续增量向量化；
- 将本地 NumPy 检索实验改造成可增量、可审计、可原子切换的后台能力；
- 为专题挖掘后台提供稳定的关键词与向量混合召回；
- 通过高层 CLI 和内网 API 隔离数据库、模型与索引细节；
- 控制一次普通 Skill 调用的时间与模型成本，不默认追求全库穷举。

### 2.2 非目标

- 第一版不部署 Qdrant、Milvus 或其他独立向量数据库产品；
- 不把相似文本在原始库中合并或删除；
- 不让分发出去的 Skill 携带模型、数据库或向量文件；
- 不让调用 Skill 的 AI 直接操作 SQL、索引参数或模型进程；
- 不因为向量化失败回滚已经成功拉取的原始反馈；
- 不把普通专题运行默认解释为“完整找出所有历史反馈”。

## 3. 已知现状与容量判断

截至设计时，远端正式 SQLite 约有 12.7 万条反馈、8.4 万个会话，数据库约 150 MiB；最近 24 小时新增约 1,465 条。服务器没有 GPU，但有 96 个 CPU 核、约 247 GiB 内存和约 48 GiB 可用磁盘。

本地实验已经验证：

- Qwen3-Embedding-0.6B 模型目录约 1.1 GiB；
- 输出为 1024 维、L2 归一化的 `float32` 向量；
- 约 5.8 万个会话的向量压缩文件约 206 MiB；
- 现有代码已经包含模型下载、断点批处理、BM25、精确余弦检索和 RRF 融合样例。

若为 12.7 万条反馈保存 1024 维 `float32` 向量，未压缩向量约 500 MiB。该规模适合单机内存映射与精确余弦检索，不需要立即引入近似索引或分布式数据库。

当前远端 cron 实际是每 2 小时拉取最近 150 分钟。本设计上线后将其替换为每 20 分钟拉取最近 30 分钟。

## 4. 方案比较与选择

### 4.1 NumPy 增量分片（采用）

SQLite 保存反馈、向量记录和分片元数据；向量以不可变 `.npy` 分片保存。检索进程内存映射所有活动分片，并对归一化向量执行精确余弦检索。小分片定期合并。

优点是最大程度复用现有实验、依赖少、结果确定、没有近似召回损失，且当前规模下查询与存储成本可控。

### 4.2 FAISS 或 HNSW

在数据量达到百万级或精确检索延迟无法满足要求时，引入增量近似索引。它能降低大规模查询成本，但第一版会增加原生依赖、索引参数、删除与重建逻辑，当前收益不足。

### 4.3 独立 Qdrant 服务

提供完整过滤、集合管理和扩容能力，但会额外引入服务部署、端口、监控、备份和版本升级。对于当前单节点和十几万条数据明显过重。

因此第一版采用 4.1，并把 4.2 作为无须改变上层 API 的后续替换路径。

## 5. 总体架构

```text
公司内网/VPN 内的调用 AI
          |
          v
Skill 随附的 feedback-topic CLI
          |
          v  HTTP，无额外令牌
feedback_hub 专题分析 API
          |
          v  仅服务器本机访问
向量检索进程
  - Qwen 模型常驻内存
  - NumPy 活动分片
  - 硬过滤后的精确余弦检索
          |
          +---- SQLite 元数据与正式 feedback 表
          |
          +---- vector_index/*.npy
```

专题分析 API 继续承担 BM25、RRF、运行快照、候选编排、后台批量语义判定、复核和导出。向量检索进程只承担查询向量生成、硬过滤后的 dense 检索和可解释排名，不直接决定专题归属。

独立进程的目的不是引入另一套数据库，而是让 0.6B 模型常驻，避免每个 CLI 请求重新加载模型，并与现有 `vector_client.py` 的 HTTP 边界兼容。

## 6. 数据同步与增量向量化

### 6.1 调度

远端调度改为：

```cron
*/20 * * * *
```

每轮执行统一流水线：

```text
拉取最近 30 分钟
  -> feedback_id 精确去重入库
  -> 提交原始数据
  -> 找出缺失当前模型向量的反馈
  -> 批量向量化
  -> 原子发布新分片
```

30 分钟窗口与 20 分钟频率产生 10 分钟重叠，用于吸收调度漂移和上游延迟。重叠不会产生重复记录或重复向量。

### 6.2 去重语义

- `feedback_id` 是入库幂等键；已有 ID 使用 `INSERT OR IGNORE`；
- 同文不同 ID 视为不同用户反馈，全部保留；
- 不在入库阶段做文本相似或语义相似合并；
- 语义聚类只用于代表性结果选择，不改变原始数据和向量记录；
- 第一版索引单条反馈，`conversation_id` 只作为上下文和结果聚合字段。

### 6.3 解耦与重试

拉取事务在模型推理前提交。向量化失败时，原始数据仍然可查询，下轮通过“缺少当前模型向量”条件自动补齐。模型推理期间不持有长数据库事务。

单机进程锁防止两轮流水线重叠执行。已有任务运行时，后启动任务记录跳过状态，不并发写分片。

## 7. 存储与一致性

### 7.1 元数据表

新增概念表如下；最终字段名可以按现有迁移约定调整，但唯一性和状态语义必须保持。

`embedding_record`：

- `feedback_id`
- `model_version`
- `content_hash`
- `shard_id`
- `row_offset`
- `embedded_at`
- 唯一键：`feedback_id + model_version + content_hash`

`embedding_shard`：

- `shard_id`
- `model_version`
- `path`
- `dimension`
- `row_count`
- `checksum`
- `state`：`building | active | retired`
- `created_at`

`embedding_sync_run`：

- 拉取窗口与实际开始、结束时间；
- 拉取数、新增数、重复数、向量化数、失败数；
- `running | succeeded | partial | failed | skipped_locked` 状态；
- 不包含原始反馈正文的错误摘要。

专题后台已有的数据覆盖记录继续用于区分“窗口成功但没有数据”和“窗口拉取失败”。

### 7.2 文件布局

```text
feedback_hub/data/vector_index/
└── qwen3-embedding-0.6b/
    ├── manifest.json
    ├── shards/
    │   ├── shard-000001.npy
    │   └── shard-000002.npy
    └── tmp/
```

SQLite 是反馈到分片行号映射的事实来源；不再维护一份重复的 JSONL 元数据。`manifest.json` 只描述查询进程应加载的已发布索引代际和活动分片。

使用未压缩 `.npy` 而非压缩 NPZ，以便内存映射和增量加载。向量在写入前做 L2 归一化。

### 7.3 原子发布

1. 在 `tmp/` 中写完整分片并计算校验和；
2. 校验维度、行数、有限值和归一化；
3. 原子重命名到 `shards/`；
4. 在 SQLite 事务中注册分片和每条反馈的行号；
5. 原子替换 `manifest.json`；
6. 查询进程加载新代际，成功后再对新请求生效。

临时文件失败时直接清理；文件已重命名但数据库未提交时会成为无引用孤儿，由启动检查清理。数据库只能引用已经存在且校验通过的文件。

小分片每天合并，或在数量超过配置阈值时合并。合并生成新代际，旧代际在没有查询引用后再标记 `retired`，因此查询不会遇到半完成索引。

## 8. 检索、时间范围与成本预算

### 8.1 时间规则

- 用户明确给出时间范围时严格使用该范围；
- 用户未给出时间时，默认最近两周；
- 同步使用的“最近 30 分钟”与专题查询范围完全独立；
- 每次结果必须报告实际查询区间、数据水位和已知覆盖缺口；
- 默认时间窗口是后台与 Skill 的版本化策略，不由调用 AI 临时猜测。

### 8.2 混合召回

硬过滤先应用于候选空间，不能先取全库 Top-K 再做时间或渠道过滤。过滤后的反馈分别进入：

- BM25/关键词召回，保证明确术语、错别字词表和精确表达；
- 向量召回，覆盖口语、隐含场景和改写；
- RRF 融合，用于安排审核顺序和代表性采样。

查询定义、正例和词语提示可以产生多个检索种子。每个候选保留检索种子、通道、原始排名和融合排名。融合排名不是相关概率，不能直接生成 `included` 结论。

### 8.3 标准模式预算

普通请求默认进入 `standard` 模式：

- 单个召回通道的初始深度为每个种子 200；
- 每次运行最多将 500 条去重候选送入后台语义分类；
- 后台分类模型沿用当前最多 20 条一批的结构化、可恢复调用；
- Skill 对有界复核队列按最多 50 条一页读取；
- 最终最多返回 100 条反馈。

候选超过预算时，后台不是简单截取融合排名前 500 条，而是在高排名基础上按时间段、渠道和语义簇做多样性选择，避免半年结果全部来自最近几天或单一重复表达。

若相关结果少于 100 条，则返回所有已确认结果。若可能存在更多结果，则返回代表性清单并明确标记：

```json
{
  "mode": "standard",
  "result_scope": "representative",
  "classified_candidates": 500,
  "returned_feedback": 100,
  "possibly_more_matches": true
}
```

标准模式不声称结果完整。时间范围变大不会线性增加后台分类量或调用 AI 的复核量，从而保证一次 Skill 调用的成本和耗时有界。

### 8.4 完整模式

只有用户明确使用“全部”“完整”“尽量拉全”等意图时，才进入 `exhaustive` 模式。后台按页扩大召回和审核预算，并持续报告进度、成本与未审核数量。达到环境配置的安全上限时必须返回 `truncated`，不得把截断结果描述为完整。

## 9. CLI 与 API 边界

### 9.1 服务器运维 CLI

```bash
python -m feedback_hub.cli pipeline incremental --pull-window 30m
python -m feedback_hub.cli ingest pull --last 30m
python -m feedback_hub.cli vectors sync
python -m feedback_hub.cli vectors status
python -m feedback_hub.cli vectors rebuild --target-model-version qwen3-embedding-0.6b-document-v2 --generation-id qwen3-embedding-0.6b-document-v2-20260721
python -m feedback_hub.cli vectors compact
python -m feedback_hub.cli vectors search --query "工具栏不会隐藏"
```

流水线命令负责锁、结构化日志、分步状态和退出码；cron 不自行拼接业务逻辑。

### 9.2 Skill CLI

```bash
feedback-topic capabilities
feedback-topic search --query "游戏全屏时工具栏不隐藏" --since 2026-01-01
feedback-topic mine --spec topic.yaml --output result.json
feedback-topic export --run-id RUN_ID --format xlsx
```

Skill CLI 是内网 HTTP 客户端，不加载模型，也不读取远端数据库。用户只需要一次性配置服务地址；由于接口保证仅能从公司内网或 VPN 访问，第一版不要求访问令牌。

### 9.3 服务接口

专题分析继续复用 `/api/topic-mining` 高层接口。内部向量进程至少提供与现有客户端兼容的：

- `capabilities`：模型、维度、索引水位、活动代际；
- `search`：查询文本、硬过滤、深度和可解释排名；
- `health/status`：模型加载、分片校验和待向量化数量。

向量接口仅绑定服务器本机地址，不直接暴露给 Skill 用户。

## 10. 后台与调用 AI 的职责

后台负责：

- 定时拉取、精确去重和增量向量化；
- 模型版本、分片、过滤、召回和融合排序；
- 候选预算、多样性采样、后台批量语义分类、运行快照和断点续跑；
- 保存判定证据、审核状态和导出文件；
- 对覆盖缺口、索引滞后和截断给出机器可读状态。

调用 Skill 的 AI 负责：

- 把用户问题整理成专题定义、纳入条件和排除条件；
- 生成少量正向、反向检索种子；
- 审核后台给出的有限边界队列并提交显式 override；
- 解释代表性清单的范围限制，不把融合排名或后台低置信度结果当成事实。

调用 AI 不需要逐条分类全部候选，也不需要掌握 SQL、embedding、向量距离、NumPy、并发或 Excel 库。普通支持工具调用和结构化输出的模型可以完成常规专题；边界密集的专题可以升级更强模型。后台分类继续复用现有 OpenAI-compatible 模型路由，Qwen3-Embedding-0.6B 只用于向量生成，不承担最终专题判定。

## 11. 故障处理与可观测性

- 拉取失败：不登记该窗口已覆盖，下轮重新拉取；
- 拉取成功、向量化失败：保留原始数据，下轮补齐；
- 索引水位落后：专题 API 明确返回滞后量和时间，不静默使用不完整索引；
- 临时或损坏分片：不进入活动 manifest；
- 模型升级：新 `model_version` 独立回填，完成后原子切换；
- 重复运行：使用进程锁和运行幂等键；
- 查询服务重启：校验 manifest、分片校验和及数据库映射后再进入健康状态；
- 日志记录运行 ID、计数、耗时、模型版本和错误码，不记录完整反馈正文；
- 状态接口报告最近成功拉取、最近成功向量化、待处理数量、活动分片和覆盖缺口。

## 12. 安全边界

- 外部专题 API 只通过公司内网或 VPN 访问；
- 第一版不加访问令牌，用户不需要提供凭据；
- 内部向量进程只绑定本机地址；
- Skill 包不包含远端地址之外的环境秘密，不包含反馈数据和模型；
- 原始反馈和导出文件沿用现有内部数据权限，不开放公网下载；
- 若未来接口暴露范围扩大，必须在不改变 Skill 业务契约的前提下增加认证、授权和审计。

## 13. 测试策略

### 13.1 数据与幂等

- 连续两次拉取相同 30 分钟窗口，第二次新增数和新增向量数均为零；
- 同文不同 `feedback_id` 都被保留；
- 同一 `feedback_id` 不产生多个当前模型向量；
- 拉取成功后模拟向量化失败，下一轮能够补齐；
- 进程锁能阻止重叠写入。

### 13.2 分片与恢复

- 写入中断不会发布临时分片；
- 校验失败分片不会进入 manifest；
- 孤儿文件可被发现和安全清理；
- 合并与模型切换期间，查询只能看到完整旧代际或完整新代际；
- 服务重启后能恢复相同检索结果。

### 13.3 检索与预算

- 时间、渠道和平台硬过滤不能被向量排名绕过；
- 未指定时间时实际范围严格为最近两周；
- 标准模式送入后台语义分类的候选不超过 500 条、导出不超过 100 条；
- 超预算结果按时间、渠道和语义簇保持多样性；
- 融合排名不会直接生成最终命中；
- 代表性结果包含 `possibly_more_matches` 和范围声明；
- 完整模式达到安全上限时返回 `truncated`。

### 13.4 质量与性能

- 使用历史工具栏专题和新增黄金样本比较 BM25、向量与融合召回的 Recall@K、Precision@K；
- 验证每个结果都可追溯到原始反馈、时间和链接；
- 在当前约 12.7 万条规模做查询延迟、并发、冷启动和增量加载测试；
- 性能阈值由首次影子运行的实测基线确定，不在设计阶段虚构固定 SLA。

## 14. 上线与回滚

1. 在不改变现有 cron 的情况下部署模型和向量进程；
2. 对现有反馈做带检查点的全量回填，期间新数据继续进入待处理队列；
3. 使用历史专题做影子检索和黄金样本评估；
4. 将 cron 从每 2 小时拉取 150 分钟切换为每 20 分钟拉取 30 分钟；
5. 观察至少一个完整业务周期的重复率、拉取延迟、向量滞后和查询耗时；
6. 启用专题 API 与 Skill CLI 的远端能力。

回滚时恢复旧 cron，并把活动 manifest 切回上一代际。向量索引是可重建派生数据，原始反馈库不随索引回滚。

## 15. 验收标准

- 远端每 20 分钟拉取最近 30 分钟，重叠窗口不重复入库；
- 新增反馈在成功拉取后自动进入当前模型索引，失败可自动补偿；
- 查询服务使用 Qwen3-Embedding-0.6B 与 NumPy 增量分片，不要求 Skill 用户安装模型；
- 用户未指定时间时使用最近两周；
