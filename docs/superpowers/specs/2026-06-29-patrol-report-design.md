# 自动巡检报告设计

## 1. 背景

当前反馈看板已经具备用户反馈入库、会话聚合、搜索、搜索报告和原始反馈跳转能力。新的目标是在已有用户反馈数据库中自动发现三类洞察：

1. 某个版本出现了某类新的问题或 bug，并呈现上升趋势。
2. 某个领域出现了可产品化的需求机会。
3. 存在值得人工优先查看的高价值用户反馈。

这些洞察需要能落回具体用户反馈。报告中的每条洞察必须附带代表反馈，用户可以从报告页跳转到看板内的会话详情页，也可以打开公司原始反馈系统链接。

## 2. 核心决策

- 第一版采用自动巡检工作流，而不是按版本或按领域的专题分析。
- 默认分析窗口为最近 7 天，对比前 14 天基线。
- 14 天对比前 30 天的中期趋势分析作为后续能力。
- 报告形态采用“报告 + 可点开的详情”，复用现有 `/reports` 页面。
- 每条洞察最多展示 5 条代表反馈，不强制凑满。
- 主题发现采用 LLM 报告级聚类，但 LLM 结果不回写正式标签表。
- 第一版手动点击生成巡检报告，稳定后再接每日自动生成。
- 稳定 LLM 打标覆盖不足是明确前置风险，必须在方案中持续暴露。

## 3. 标签风险与双轨模式

`L1`、`L2`、`severity` 依赖 LLM 打标，但当前历史与近期反馈并未稳定完成打标。这会显著影响自动巡检报告的可信度：

- 问题趋势不能直接依赖 `L1=A.Bug` 或 `L2` 分桶，否则漏标会让趋势失真。
- 需求机会不能直接依赖 `L1=B.建议`，否则会漏掉大量自然语言诉求。
- 高价值反馈不能直接依赖 `severity=P0/P1`，否则会错过未打标但信息密度高的反馈。

因此巡检报告采用双轨模式：

### 3.1 探索模式

当标签覆盖不足时，报告进入探索模式。

- 候选召回主要依赖原始文本、版本、平台、时间、会话长度、链接和反馈元数据。
- `L1/L2/severity` 只作为弱参考。
- 趋势措辞使用“疑似”“可能上升”“新增信号”。
- 前端展示明显的质量提示。
- 报告可用于发现线索，但不能作为稳定巡检结论。

### 3.2 稳定模式

当当前窗口和基线窗口都满足标签覆盖门槛后，报告进入稳定模式。

建议质量门槛：

- 最近 7 天会话级标签覆盖率大于等于 90%。
- 前 14 天基线会话级标签覆盖率大于等于 90%。
- 待定或低置信标签比例小于等于 20%。

稳定模式下，`L1/L2/severity` 可以参与主排序、主题分桶和趋势解释。报告措辞可以使用“新增”“上升”“集中出现”。

## 4. 产品入口

复用现有 `/reports` 页面。

第一版新增一个按钮：

```text
生成巡检报告
```

点击后创建 `patrol` 类型异步报告任务，默认参数为：

```json
{
  "current_days": 7,
  "baseline_days": 14,
  "max_feedback_per_insight": 5
}
```

报告列表、任务状态、失败重试、详情打开继续复用现有报告页能力。

## 5. 报告结构

巡检报告详情页分为四层。

### 5.1 质量提示

展示本次报告模式、标签覆盖率和主要风险。

探索模式提示示例：

```text
L1/L2/severity 覆盖不足，本报告主要基于文本候选和 LLM 聚类，仅供探索。
```

### 5.2 巡检摘要

展示：

- 当前窗口和基线窗口。
- 当前窗口反馈量和会话量。
- 基线窗口反馈量和会话量。
- 当前窗口和基线窗口的打标覆盖率。
- 生成出的洞察数量。

### 5.3 三类洞察

报告按三类洞察分组展示：

1. 新增或上升问题。
2. 需求机会。
3. 高价值反馈。

每条洞察包含：

- 标题。
- 类型。
- 摘要。
- 为什么值得关注。
- 证据指标。
- 涉及版本和平台。
- 可信度。
- 局限性。
- 代表反馈列表。

### 5.4 代表反馈

每条洞察最多展示 5 条代表反馈。每条代表反馈包含：

- `conversation_id`
- `feedback_id`
- 文本摘要或摘录
- 版本
- 平台
- 时间
- `external_chat_url`

前端提供两个动作：

- 查看详情：跳转 `/feedback/{conversation_id}`。
- 原始反馈：打开 `external_chat_url`。

如果 `external_chat_url` 缺失，只展示“查看详情”。

Markdown 文本版继续保留，用于复制和转发；前端优先渲染结构化洞察。

## 6. 后端模型与接口

巡检报告复用现有 `search_report_job` 基础能力，而不是新建完全平行的报告系统。

可以扩展现有表字段，或在实现时迁移成更通用的 `report_job`。第一版建议最小改动扩展 `search_report_job`：

```text
report_kind              search | patrol
patrol_window_json       当前窗口、基线窗口、生成模式等
structured_result_json   结构化洞察结果
quality_gate_json        打标覆盖、可信度、风险提示
```

新增接口：

```text
POST /api/search-reports/patrol
```

请求体：

```json
{
  "title": "自动巡检报告",
  "current_days": 7,
  "baseline_days": 14,
  "max_feedback_per_insight": 5
}
```

返回：

```json
{
  "id": "report_xxx",
  "status": "pending"
}
```

继续复用：

```text
GET /api/search-reports
GET /api/search-reports/{job_id}
POST /api/search-reports/{job_id}/retry
```

巡检报告详情额外返回：

```text
report_kind = patrol
structured_result
quality_gate
```

## 7. 结构化结果格式

`structured_result_json` 示例：

```json
{
  "mode": "exploratory",
  "window": {
    "current_days": 7,
    "baseline_days": 14,
    "current_from": "2026-06-22",
    "current_to": "2026-06-29",
    "baseline_from": "2026-06-08",
    "baseline_to": "2026-06-22"
  },
  "sections": [
    {
      "type": "rising_issue",
      "title": "疑似某版本语音识别问题上升",
      "summary": "最近 7 天内多条反馈提到语音识别不准或无法转文字。",
      "why_it_matters": "该问题集中在核心输入能力，且有版本集中迹象。",
      "evidence": {
        "current_count": 18,
        "baseline_count": 6,
        "growth_ratio": 3.0,
        "versions": ["3.5.0"],
        "platforms": ["iOS"]
      },
      "confidence": "medium",
      "limitations": ["当前标签覆盖不足，主题主要来自文本聚类。"],
      "representative_feedback": [
        {
          "conversation_id": "conv_xxx",
          "feedback_id": "fb_xxx",
          "summary": "用户反馈语音输入识别不准。",
          "text_excerpt": "语音输入老是识别错...",
          "appversion": "3.5.0",
          "platform": "iOS",
          "ts_ms": 1782700000000,
          "external_chat_url": "https://wrfeedback.weread.woa.com/chat?..."
        }
      ]
    }
  ]
}
```

洞察类型：

```text
rising_issue
opportunity
high_value_feedback
```

没有代表反馈的洞察必须丢弃。

## 8. 候选召回

第一版候选召回不依赖标签作为唯一入口，分三路。

### 8.1 问题和 bug 候选

基于负向体验和故障表达召回，例如：

```text
不能、无法、闪退、卡、没反应、识别不准、丢失、异常、失败、崩、用不了
```

再结合版本、平台和时间窗口进行统计。

### 8.2 需求机会候选

基于愿望、缺口、比较、迁移表达召回，例如：

```text
希望、能不能、建议、想要、为什么不支持、缺少、能否、还是 XX 好用、想换、如果能
```

需求候选不要求是负向反馈。

### 8.3 高价值反馈候选

按信息密度召回：

- 文本较长。
- 有版本、平台或设备信息。
- 包含复现步骤或明确场景。
- 有附件、截图、视频或原始链接。
- 同一用户近期多次反馈。
- 包含竞品对比或迁移倾向。
- 情绪强烈且内容具体。

稳定模式下再叠加标签：

- `L1=A.Bug` 强化问题候选。
- `L1=B.建议` 强化需求候选。
- `severity=P0/P1` 强化高价值候选。
- `L2` 用于领域归类和趋势分桶。

## 9. 趋势判断

探索模式采用保守阈值：

- 当前窗口计数大于等于 3。
- 当前窗口日均数量相比基线日均至少 2 倍。
- 或基线为 0 且当前窗口达到最小样本数，标为新增信号。
- 同一主题若集中在某版本，报告中标明版本集中。
- 主题无法稳定归类时，只标为疑似，并展示代表反馈。

稳定模式可以提高阈值：

- 当前窗口计数大于等于 5。
- 增长倍数大于等于 2。
- 或当前窗口占全量比例明显高于基线。
- 打标覆盖达标后，才输出明确上升。

## 10. LLM 洞察生成

LLM 只处理后端召回出的候选集合，不处理全库。

每条样本输入：

```text
conversation_id
feedback_id
时间
版本
平台
设备
弱参考标签
原文摘要或截断文本
是否有原始反馈链接
基础召回原因
当前和基线统计
```

LLM 必须输出结构化 JSON。每条洞察必须包含：

```text
type
title
summary
why_it_matters
evidence
confidence
representative_feedback
limitations
```

服务端需要校验 LLM 输出：

- `type` 必须属于允许枚举。
- 代表反馈必须能匹配输入候选的 `conversation_id`。
- 每条洞察代表反馈最多 5 条。
- 没有代表反馈的洞察丢弃。
- 无法解析 JSON 时报告任务失败，可重试。

## 11. 高价值反馈定义

第一版高价值反馈定义为“值得人工优先查看”，不等同于严重等级。

高价值信号包括：

- 描述清楚，可复现。
- 可能影响核心能力或较大用户面。
- 涉及新版本、新平台或关键设备。
- 包含竞品对比或迁移倾向。
- 强烈情绪但内容具体。
- 包含附件、截图、视频或原始链接。
- 长文本且包含明确使用场景。

## 12. 任务服务

新增 `feedback_hub/search/patrol_report_service.py`。

职责：

- 计算当前窗口和基线窗口。
- 审计打标覆盖，判定探索模式或稳定模式。
- 召回候选反馈。
- 计算趋势指标。
- 调用 LLM 生成结构化洞察。
- 校验和裁剪 LLM 输出。
- 生成 Markdown 文本版。
- 写回 report job。

## 13. 错误处理

- LLM 失败：报告任务标记为 `failed`，允许重试。
- 数据不足：报告任务 `succeeded`，但结构化结果显示未发现稳定洞察。
- 标签不足：不失败，进入探索模式。
- 个别洞察无代表反馈：服务端丢弃。
- `external_chat_url` 缺失：前端隐藏“原始反馈”动作。
- 结构化 JSON 解析失败：报告任务失败，并记录错误信息。

## 14. 测试策略

后端测试：

- 创建巡检报告任务成功。
- 当前窗口和基线窗口计算正确。
- 标签覆盖率审计能判定探索模式和稳定模式。
- 候选召回不依赖标签也能返回文本候选。
- 趋势阈值过滤小样本噪声。
- LLM 输出校验会丢弃无代表反馈的洞察。
- 巡检报告详情返回 `report_kind`、`structured_result`、`quality_gate`。

前端测试：

- 报告页展示“生成巡检报告”按钮。
- 巡检报告列表与搜索报告共存。
- 探索模式展示质量提示条。
- 洞察卡片按三类分组展示。
- 代表反馈能跳转 `/feedback/{conversation_id}`。
- `external_chat_url` 存在时展示原始反馈动作。

## 15. 后续能力

- Phase 0：补齐稳定 LLM 打标与覆盖审计。
- Phase 1：实现手动生成巡检报告。
- Phase 2：支持 14 天 vs 前 30 天的中期趋势报告。
- Phase 3：支持每日自动生成和推送。
- Phase 4：支持按版本、领域或平台触发专题巡检。
- Phase 5：将稳定洞察沉淀为可追踪的问题或需求卡片。
