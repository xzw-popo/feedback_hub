# 日报洞察信号层设计

日期：2026-07-16

## 1. 背景与结论

2026-07-07 预热加 2026-07-08 至 2026-07-14 七日影子运行已经跑通动态主题链路。报告期内共处理 4,084 个问题单元，形成 2,895 个当日原子主题；最终稳定主题库包含 1,887 个主题。

这批结果说明：

1. 动态主题可以从反馈中产生，并跨日延续，不需要固定主题表。
2. 原子主题数量天然较多。最终主题库中 71.9% 的主题只有一个去重会话，只有 23.3% 在多个日期出现。
3. 原子主题回答“用户在说哪些可独立处理的问题”，不直接回答“今天哪些内容值得主动打扰产品同学”。
4. `report_candidate`、`report_policy` 或 message 级标签均不能直接承担最终日报准入判断。

因此，在动态主题层与最终日报之间新增独立的“日报洞察信号层”。该层不修改主题记忆，只在给定报告日和历史窗口内召回、归并、判断和编排值得进入日报的信号。

## 2. 实验目标

第一轮使用 2026-07-14 作为报告日，以 2026-07-07 至 2026-07-13 作为历史基线，验证以下命题：

1. 能从约 400 个当日原子主题中召回有限且可解释的日报候选。
2. 能把多个相关但边界不同的原子主题，在不改写主题库的前提下组合为一条报告洞察。
3. 能区分新问题、上升或重复问题、需求机会和高价值单条反馈。
4. 最终正文不超过 5 条，不为凑数强制填满。
5. 每条洞察都能跳转到对应原始会话，并明确陈述入选依据和证据限制。

本轮是离线实验，不发布正式日报，不部署定时任务。

## 3. 核心对象

### 3.1 原子主题

原子主题沿用动态主题链路中的定义：可以由同一次调查、修复或产品决策处理的一组问题单元。它具有稳定 `topic_id`，负责跨日记忆和检索。

原子主题可以很细，也允许长期处于单例状态。它不是最终日报的一条内容。

### 3.2 日报信号候选

日报信号候选是规则基于当日主题、历史主题和原始问题单元宽召回出的待判断对象。一个候选可以是：

- 一个原子主题；
- 一个原子主题在当天的新增证据；
- 若干相互关联、适合在报告中共同解释的原子主题组。

候选进入模型判断不代表最终进入日报。

### 3.3 报告洞察

报告洞察是面向产品同学的最终表达单元。它可以引用一个或多个原子主题，但必须有一个清晰的产品含义、判断依据和原始证据。

报告层的归并只影响展示，不产生 `topic_merged`，也不改变稳定主题 ID、成员关系或生命周期历史。

## 4. 输入与时间窗口

实验读取现有七日影子运行产物：

- 报告日的 `daily_topics.jsonl`；
- 报告日和历史日的 `lifecycle_decisions.jsonl`、`topic_events.jsonl`；
- 每日 `issue_units.jsonl`；
- 报告日结束后的 `topic_store.jsonl`；
- `low_information_pool.jsonl` 和 `media_appendix.jsonl`；
- 本地主题及问题单元向量。

第一轮窗口固定为：

- 报告日：2026-07-14；
- 观察基线：2026-07-07 至 2026-07-13；
- 统计单位：去重 `conversation_id`，不按 message 数量计数。

报告日之后可以将窗口参数化。日报默认使用最近 7 个完整自然日作为短期基线；周报门槛另行设计。

## 5. 信号类型

候选模型只能从以下主要类型中选择，不发明新的主类型：

| `signal_type` | 含义 | 关键证据 |
|---|---|---|
| `new_bug` | 基线中没有可靠承接、当天出现的明确问题 | 问题明确、证据可行动；单例也可进入 |
| `rising_or_repeated_bug` | 当天重复、跨日持续、重新出现或相对基线上升的问题 | 去重会话数、活跃日期、历史计数和当天增量 |
| `demand_opportunity` | 值得考虑的新需求或改进机会 | 目标场景、用户要完成的任务、现有能力缺口 |
| `high_value_single` | 频次不高但信息完整、影响或产品价值明显的单条反馈 | 具体场景、行为、预期、复现线索或高价值工作流 |
| `not_reportable` | 可检索但不值得进入本次日报正文 | 信息弱、重复价值低、不可行动或不适合主动推送 |

`severity` 不作为必需标签。模型判断的是“本次日报是否值得关注”，不声称已经确定真实影响范围、修复优先级或可解决性。

## 6. 两阶段候选生成

### 6.1 第一阶段：确定性统计与宽召回

规则只做可复现的统计和高确定性排除，不直接决定最终正文。为每个当日主题计算：

- 当日问题单元数和去重会话数；
- 历史 7 日逐日去重会话数；
- 首次出现、最近出现和活跃天数；
- 当天是否为 `new_topic`、`same_topic`、`possible_subtopic` 或 `uncertain`；
- 平台、版本和功能候选分布；
- Bug、需求和改进诉求构成；
- 证据摘要数量、模型置信度和人工复核标记；
- 是否包含媒体证据；
- 可点击原会话链接数量。

规则采用多路召回，而不是依赖一个加权总分：

1. **重复路**：当日去重会话数达到观察门槛的主题；日报第一版允许 2 个会话进入候选，不等于必然入选。
2. **跨日路**：历史窗口内持续、间隔后重新出现，或当天计数高于自身短期基线的主题。
3. **新增路**：生命周期为 `new_topic` 且文本证据清晰的主题。
4. **需求路**：包含明确 `feature_request` 或 `improvement_request` 的主题。
5. **高价值单条路**：单例但包含具体场景、明显阻断、数据丢失、兼容性、回归线索或完整工作流证据的主题。
6. **边界补偿路**：从相似主题和 `possible_subtopic` 关系中召回可能应在报告层共同解释的兄弟主题。

同一主题可以命中多路，合并后只保留一个候选记录及全部召回原因。

以下情况可以确定性排除正文竞争，但仍保留审计记录：

- 已被明确配置为“不进入报告”的功能政策；
- 纯客服回复或非用户证据；
- 已确认无效、无产品含义或完全不可理解的文本；
- 只有媒体且文本无法判断的问题，转入媒体附录。

功能政策为“可以进入报告”时只表示有资格参与竞争，不保证入选。

### 6.2 第二阶段：相近候选归并建议

对宽召回候选使用已有向量进行近邻召回，结合以下关系生成可能的“报告洞察组”：

- 指向同一历史主题；
- 具有父主题或 `possible_subtopic` 关系；
- 向量高度相似；
- 标题不同但描述的是同一用户任务、症状链或产品决策。

模型判断候选是否适合在报告中共同表达。允许：

- 合并为一条洞察；
- 保持为不同洞察；
- 只保留其中证据更强的一条；
- 判为边界不确定并进入人工复核。

不能仅因功能相同而归并。Bug 与需求默认分开；只有它们共同指向同一个明确能力缺口、且合并后不会掩盖问题性质时，才允许同组展示。

## 7. 主题级 LLM 编辑判断

模型输入不是单条 message，而是一个候选洞察包，包括：

- 原子主题标题和描述；
- 当日及历史计数；
- 生命周期和召回原因；
- 代表问题单元摘要及证据片段；
- 平台、版本、功能候选和反馈类型分布；
- 媒体存在性和证据链接；
- 相近主题及关系；
- 功能报告政策。

这一阶段负责候选理解、报告层归并和局部提名，不负责决定最终正文。模型输出固定 schema：

```json
{
  "insight_id": "insight:2026-07-14:001",
  "report_decision": "nominate | observe | exclude | manual_review",
  "signal_type": "new_bug | rising_or_repeated_bug | demand_opportunity | high_value_single | not_reportable",
  "headline": "简洁、可核验的标题",
  "summary": "发生了什么以及为什么值得关注",
  "selection_reason": "入选、观察或排除依据",
  "trend_claim": "none | new_signal | repeated | persistent | reappeared | rising",
  "trend_evidence": {
    "today_conversations": 0,
    "baseline_daily_counts": [],
    "active_days": 0
  },
  "source_topic_ids": [],
  "representative_issue_unit_ids": [],
  "confidence": 0.0,
  "needs_human_review": false
}
```

判断约束：

- 不把“当天首次匹配不到历史主题”直接写成产品层面的“全新问题”；
- 没有足够历史计数时不得声称“上升”；
- 不从单条反馈推断总体影响范围；
- 不因为措辞强烈就推断高优先级；
- 允许基于完整、具体证据把单例判为高价值；
- `nominate` 表示值得进入全局终选，不等同于最终正文；
- `observe` 表示局部模型不主动提名；若确定性证据足够强，仍可由 shortlist 规则补召回；
- 信息或边界不足时使用 `manual_review`，不得强行补事实。

模型调用必须记录渠道、模型、提示词版本、耗时、重试和解析状态，不保存凭据。

## 8. 全局终选与编排

### 8.1 为什么需要独立终选

主题级编辑模型每次只看到一个关系组或少量单例，能够判断候选本身是否成立，却无法比较当天所有候选的相对价值。2026-07-14 首轮运行中，局部模型产生了 105 条 `main` 判断，产物层随后按信号类型和置信度截取 5 条，并把其余 100 条降为观察项。这种截取没有完成全局价值比较，且会因为类型排序而遗漏频次更高或产品意义更强的需求和问题。

因此，原局部 `main` 语义改为 `nominate`。最终正文只能由独立的全局终选阶段产生，产物渲染层不得自行截取局部提名。

### 8.2 确定性 shortlist

终选前先生成最多 30 条的 shortlist，控制模型上下文并保留多类信号的竞争机会。shortlist 是宽松召回，不是正文配额；最终报告不强制覆盖每类信号。

shortlist 从全部局部洞察中按四条独立通道召回：

1. **重复或趋势问题**：优先有 `rising`、`reappeared`、`persistent` 或 `repeated` 证据的明确 Bug；按当天去重会话数、历史活跃天数、历史总会话数和模型置信度依次排序。
2. **新问题**：优先当天去重会话较多、证据片段完整、上下文明确且无需人工复核的 `new_bug`。
3. **需求机会**：按当天去重会话数、历史活跃天数、历史总会话数和模型置信度依次排序，并保留具体用户任务与能力缺口。
4. **高价值单条**：只召回来源链接、场景、行为或预期较完整，且无需人工复核的单条反馈。

每条通道使用独立的字典序规则，不计算不可解释的统一重要性分数。默认上限分别为 10、8、8、4 条，跨通道或高度相近洞察去重后总数不超过 30。所有非 `exclude`、非 `manual_review` 的局部洞察都按证据字段参与本通道排序；`nominate` 只在其他证据相同时作为优先条件。这样，证据更强的 `observe` 可以进入 shortlist，局部批次判断不会成为硬门槛。

shortlist 每行必须包含：局部洞察 ID、标题、摘要、信号类型、趋势口径、当日及历史去重会话数、活跃天数、功能与平台分布、代表证据摘要、来源链接数量、局部决定、置信度和人工复核标记。

当结构化功能仍为 `unknown_feature` 时，允许使用高确定性文本规则补充 `report_priority`，但不把它冒充功能事实。皮肤、纯视觉主题和纯账号登录偏好标记为低报告优先级；它们不会仅凭高频进入正文，但明确功能损坏或异常新信号仍可参与全局比较。

### 8.3 全局 LLM 终选

全局终选模型一次看到完整 shortlist，横向比较：

- 产品影响和可行动性；
- 问题的明确程度与证据强度；
- 当天信息增量，包括新出现、重新出现、持续或上升；
- 需求背后的用户任务与能力缺口；
- 与其他候选的重复程度；
- 是否值得主动打扰产品同学，而不只是可以进入报告。

模型最多选择 5 条，也可以选择 0 条。不得为了类型多样性凑数，也不为 Bug、需求或高价值单条预留固定正文名额。同等条件下可以优先明确异常与有时间增量的信号，但不能仅按频次或置信度排序。

终选输出固定 schema：

```json
{
  "selected_insights": [
    {
      "insight_id": "insight:2026-07-14:001",
      "rank": 1,
      "selection_reason": "相对于其他候选更值得今日主动关注的原因",
      "editorial_note": "必要的证据限制或表达调整",
      "report_summary": "不含频次数字、只复述已提供事实的正文摘要"
    }
  ],
  "selection_summary": "本日整体取舍说明"
}
```

解析器必须验证：

- 选中 ID 全部来自 shortlist，且不重复；
- 数量为 0 至 5，`rank` 连续且唯一；
- 选中洞察不带 `needs_human_review`，并至少有一个有效原会话链接；
- 标题、信号类型和趋势结论沿用已验证的局部洞察，终选模型不能发明新事实或扩大趋势；
- `selection_reason` 不得引用模型置信度，不得决定 severity、修复优先级或实施紧迫性；获客、留存和流失判断必须有用户转用、卸载或停止使用等直接证据；
- `report_summary` 不重复频次数字，正文频次只使用确定性统计字段；
- 高度相近或来源候选重叠的洞察不能同时入选。

全局终选调用失败、解析失败或校验失败时，进行有限重试；最终仍失败则将报告标记为 `selection_blocked`，保留 shortlist 和失败记录，不使用确定性排序自动生成正文。

### 8.4 最终编排

正文最多 5 条，不设置最低条数，也不为每种信号类型预留固定名额。

最终选择遵循以下原则：

1. 先保证证据可靠和判断可解释；
2. 同等条件下优先明确 Bug、真实上升或持续信号；
3. 需求机会需要说明用户任务和能力缺口；
4. 高价值单条可以越过频次门槛，但必须信息完整；
5. 高度相近的洞察只保留一个主条目；
6. `manual_review` 不进入 shortlist 或正文；
7. 不能被正文承载的候选留在观察池和检索层。

第一轮不使用难以解释的单一综合分数。规则提供可审计 shortlist，局部 LLM 负责理解与提名，全局 LLM 负责相对比较和最终排序。渲染层只消费终选结果，不再依据类型或置信度自行截断。

## 9. 报告结构

2026-07-14 日报草稿包含：

1. **今日重点**：最多 5 条洞察，每条包含标题、类型、核心判断、统计证据、代表反馈链接和必要的证据限制。
2. **继续观察**：少量接近正文门槛、需要更多天数据或人工判断的信号。
3. **媒体附录**：带图片或视频但仅凭文本无法判断的问题，与正文候选分开。
4. **运行说明**：数据范围、去重口径、历史窗口和模型渠道，不展示内部凭据或冗长技术日志。

报告不得把原子主题总量、模型置信度或规则命中次数直接包装成产品结论。

实验输出到独立目录：

`outputs/daily_insight_signal_20260714/`

至少包含：

- `candidate_recall.jsonl`：宽召回候选和召回原因；

- `insight_decisions.jsonl`：模型判断和渠道信息；
- `global_shortlist.jsonl`：进入全局比较的有限候选及各通道召回依据；
- `global_selection.json`：最终选中洞察、排序和相对选择理由；
- `daily_insight_review.xlsx`：人工 Review 表；
- `daily_report_draft_20260714.md`：日报草稿；
- `run_summary.json`：数量漏斗、失败与解析统计。

Review 表包含四个工作表：

- `正文与观察`：最终正文、观察池及人工结论列；
- `全部候选`：所有候选、召回原因、模型判断和排除原因；
- `原子主题关系`：被组合到同一洞察的主题及关系证据；
- `媒体附录`：文本不足但带媒体的反馈。

每条候选至少保留一个可点击原会话链接。人工列包括：

- `human_report_decision`；
- `human_signal_type`；
- `human_grouping_result`；
- `human_notes`。

Codex 先复核明确案例并填写建议；真正模棱两可的行留给用户判断。

## 11. 失败与降级

- 确定性统计必须覆盖所有报告日主题，漏行或重复 ID 时停止生成报告。
- 模型解析失败时进行有限重试和小批拆分，不回退为语义标签。
- 单个候选最终失败时进入显式失败清单，不静默排除。
- 全局终选失败时报告状态为 `selection_blocked`，不以局部提名或确定性排序代替最终正文。
- 趋势历史不完整时降级为 `repeated`、`new_signal` 或 `none`，不得输出 `rising`。
- 证据链接缺失时不能进入正文，保留在数据质量清单。
- 模型渠道切换不改变 schema 和判断口径，产物记录实际 route。

## 12. 验收标准

### 12.1 数据与追溯

- 2026-07-14 的 404 个当日主题全部进入统计特征表且只出现一次；
- 候选、洞察、问题单元、conversation 和原链接之间可以完整追溯；
- 所有频次按去重 conversation 计算；
- 所有 `rising` 判断都有完整逐日基线支持；
- 所有正文条目至少有一个有效原会话链接；
- 产物不包含 API key、token 或 Agent 凭据。

### 12.2 日报质量

- 正文不超过 5 条且允许为空或少于 5 条；
- shortlist 不超过 30 条，且每条可以追溯到独立召回通道和排序字段；
- 正文条目全部来自合法全局终选结果，局部提名不能被渲染层直接截取为正文；
- 全局终选结果覆盖所有选中 ID、排序连续且没有来源重叠的重复洞察；
- 正文中不存在仅因功能相同而误合并的明显案例；
- “新问题”和“上升趋势”没有超出数据证据的表述；
- 单例入选必须在 Review 表中给出具体价值依据；
- 每个未入选候选都有可理解的排除或观察原因；
- 用户对正文候选的直接接受或仅需轻微改写比例以 80% 为实验目标；
- 任何无证据趋势结论均视为阻断性问题，不以总体接受率抵消。

### 12.3 主题层隔离

- 报告层归并不修改 `topic_store.jsonl`；
- 不生成未经复核的 `topic_merged` 或 `topic_split` 事件；
- 旧 `report_candidate` 只可作为辅助解释字段，不作为召回或准入硬门槛；
- 功能政策“可以进入报告”不被解释为必然进入。

## 13. 本轮不做

- 不重跑或全局重聚类七日原子主题；
- 不设计正式周报门槛；
- 不读取图片或视频内容；
- 不建立固定全局主题分类表；
- 不部署定时任务或写入生产数据库；
- 不使用不可解释的统一重要性分数替代证据判断；
- 不把模型的日报判断反向写成事实标签。
