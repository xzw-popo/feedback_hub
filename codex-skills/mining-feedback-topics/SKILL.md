# Mining Feedback Topics

Use the bundled client. Do not query source databases or vector tools directly. The packaged internal default works on company network/VPN; `FEEDBACK_TOPIC_API_URL` is an optional override and `FEEDBACK_TOPIC_API_TOKEN` is unused for the current internal deployment. For plan-only requests, do not claim artifacts, results, or validation. Do not expand the user's named object into a different object or product. Keep each user-named target object and behavior as required inclusion conditions; put unrequested adjacent objects or behaviors only in exclusion criteria.

A blocked pre-run response contains four slots: proposed inclusion, proposed exclusion, one material scope question when needed, and the service or configuration blocker. Treat an explicit relative time range as supplied scope; resolve whole-day relative ranges from `available_through`. Never use the Agent's system or local current time. With no boundaries, default to the most recent 14 days using capabilities `default_time_days=14`; never default to all history. When exactly one boundary is supplied or timezone is unknowable, ask: “What start time, end time, and timezone should this run use?”

1. **Capabilities.** Run [topic_backend_client.py](scripts/topic_backend_client.py) with `capabilities`. Confirm schema versions, formats, statuses, read-only flags, limits, the canonical platform contract, and ready `source_freshness.available_through`.
2. **Validate.** Read the [topic spec](references/topic-spec.md). Use `unit: feedback`. Populate each hard-scope field only with values explicit in the current request; leave every other hard-scope field empty. Preserve platform intent; `prepare-spec` resolves canonical spelling. Use `mode: standard` unless the user explicitly requests all, complete, or exhaustive results; only then use `mode: exhaustive`. Six months alone is not exhaustive. Run `prepare-spec --spec TOPIC_SPEC_PATH --output PREPARED_SPEC_PATH`; add `--window-days DAYS` for a whole-day range. The client calls [validate_topic_spec.py](scripts/validate_topic_spec.py), anchors absent times, canonicalizes platform aliases, and writes a separate file. Unsupported or ambiguous platforms block creation; repair scope instead of removing them.
3. **Create.** Run `create-run --spec PREPARED_SPEC_PATH`. Reuse its ID; never replace a running run.
4. **Inspect.** Read the [backend contract](references/backend-contract.md); copy client commands from the backend contract verbatim. Poll `get-run RUN_ID`; inspect funnel counts, data cutoff, vector watermark, and unresolved failures. For `paused_quota_exhausted` or another repairable `failed` run, repair the reported service/configuration blocker and `resume RUN_ID` on the original run. Do not create a replacement run in the same source generation. Source coverage/readiness failures require backend preparation, then a new create attempt.
5. **Review.** Read the [review policy](references/review-policy.md). The backend bounds sampled QA and retains mandatory review. Fetch `review-queue RUN_ID --output FILE --offset OFFSET --limit 50` until `next_offset` is null. Review every `source_item` plus `context_items`; merge all page decisions, then submit once with `apply-overrides RUN_ID --file FILE`.
6. **Verify.** Run `verify RUN_ID`. Completion requires zero data coverage gaps and stale-index violations, exact classification coverage, verified source evidence, and valid links; otherwise report incomplete.
7. **Export.** Run `export RUN_ID --format xlsx|jsonl`, then `download RUN_ID ARTIFACT --output FILE`.
8. **Deliver.** Provide the artifact, run ID, cutoff, counts, and limitations. Copy only these five backend-returned fields: `mode`, `result_scope`, `matched_total`, `returned_feedback`, `possibly_more_matches`. Preserve `result_scope=reviewed` or `result_scope=representative`; never invent a result_scope value. Representative is not complete. Do not write formal labels. Candidate tuning remains backend-owned.
